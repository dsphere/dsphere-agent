# Saved application account tools

Invoke the account methods directly from `references/capabilities/dsagent.accounts.*.md`, like every other known method; look a contract up with `dsagent_list_capabilities` (`method` plus `detail=invoke`) only after `INVALID_REQUEST` or `CAPABILITY_UNAVAILABLE`. An older Extension/Biz can refuse unsupported methods; do not emulate them by calling arbitrary APIs or clicking Work settings.

1. `dsagent.accounts.options.get` lists permitted existing applications and current creation conditions; templates that would create another application are outside this phase. `list` searches the Work-visible snapshot. Use only returned `appId`/`accountId` references and `allowedActions`.
2. `get` and `fingerprint.get` return sanitized current configuration. Account names may be business data: do not log them.
3. Ordinary `create` always opens a trusted configuration form. Read the selected application's `options.get` and call `create` with its returned `appId`, `reviewConfiguration=true` and any known non-secret prefills; The person always reviews the application first; a supplied `appId` is only a prefill and can be changed before the application-specific form. Omit `appId` when the application is unknown. Frontend and Sidepanel show the permission-derived controls; when neither is visible the extension opens the existing Sidepanel Chat and shows an inline form. Do not substitute chat questionnaires or finish at an options catalog. The form shows supported login methods, remark, assignment, permitted device/proxy or local network, sync/session retention and fingerprint metrics. The options `configurationText` describes each field, values, defaults and conditions for all AI callers. Use actual choices only and explain `blockedReasons` instead of attempting a write with missing resources.
   Explicit generation such as “随便创建一个美团账号” permits `generateDefaults=true` for the named application's returned reference. The owner generates a DSphere account name, encrypted password and permitted defaults locally, then saves directly without form/confirmation/password prompts. Only explicit delegation such as “随便挑一个应用创建” permits `chooseAnyApplication=true` together with `generateDefaults=true`. Otherwise an omitted app opens an application picker. This creates a DSphere record, never registers a third-party account. Generated creation refuses an observed duplicate and preserves explicitly requested supported non-secret values. Current permissions/resources are rechecked before dispatch.
   Ordinary creation still requires the person's independent confirmation and private password input; never answer those dialogs yourself. `VERIFICATION_CODE` does not request a password. No password, ciphertext, cookie, internal tag, header or credential reference is an MCP argument or result. `not-dispatched` / `input-required` means no business write was sent; use its missing fields and blocked reasons to correct the request only in this explicitly undispatched case. `update` merges permitted profile changes; `replaceCredential=true` requests trusted private input. Missing, declined or expired confirmation does not authorize continuation.
4. For an explicit deletion request, resolve a unique account from `list` and call `delete` directly. Built-in and external Agents delete without a confirmation dialog or a second chat confirmation. Do not read `get` just to print details. If the target is ambiguous, ask only which account. Current permissions, target occupancy and cancellation checks still apply. On `succeeded`, reply in one short sentence and stop, without further lookups. On `partial` with `data.saved=true`, report “account deleted; environment cleanup pending”; never delete again. `set-enabled` reads the target, toggles at most once when needed, and verifies it. The current APIs do not provide cross-client atomic set, create-only or global exactly-once semantics.
5. `open` uses the existing account environment/fill owner. A page-opened result proves neither autofill nor login. `close` reuses synchronization and reports warnings while preserving uncertain contexts for recovery. `focus` locates existing account pages; it does not open a new environment.
6. `fingerprint.update` merges only advertised fields. `fingerprint.regenerate` follows the current Work baseline. Already-open environments follow existing activation rules. Cookies and unsupported fields are refused.
7. Every write uses a fresh bounded idempotency key. Keep the returned operation reference; inspect `operations.get` under the same caller/session only when the result is pending or unknown. A timeout may have taken effect: use the gateway's operation reference for read-only lookup and check current state. Never repeat a deletion, toggle or open under another key to recover from an unknown result. `partial`, `waiting-user`, `failed`, `cancelled` and `outcome-unknown` do not mean full completion; a partial result may still confirm deletion as described above. Local operation records are not server receipts.

Required human interactions appear in the conversation for non-secret configuration, with separate trusted consent/credential input where required. Explicit deletion executes directly without these interactions. Frontend and Sidepanel share the same Extension account owner through the in-process tool surface; external AI reaches that owner through the existing Native MCP gateway. Native contains no account business implementation.
