# Saved application account tools

Invoke the account methods directly from `references/capabilities/dsagent.accounts.*.md`, like every other known method; look a contract up with `dsagent_list_capabilities` (`method` plus `detail=invoke`) only after `INVALID_REQUEST` or `CAPABILITY_UNAVAILABLE`. An older Extension/Biz can refuse unsupported methods; do not emulate them by calling arbitrary APIs or clicking Work settings.

1. `dsagent.accounts.options.get` lists permitted existing applications and current creation conditions; templates that would create another application are outside this phase. `list` searches the Work-visible snapshot. Use only returned `appId`/`accountId` references and `allowedActions`.
2. `get` and `fingerprint.get` return sanitized current configuration. Account names may be business data: do not log them.
3. Ordinary `create` always opens a trusted configuration form. Read the selected application's `options.get` and call `create` with its returned `appId`, `reviewConfiguration=true` and any known non-secret prefills; The person always reviews the application first; a supplied `appId` is only a prefill and can be changed before the application-specific form. Omit `appId` when the application is unknown. Frontend and Sidepanel show the permission-derived controls; when neither is visible the extension opens the existing Sidepanel Chat and shows an inline form. Do not substitute chat questionnaires or finish at an options catalog. The form shows supported login methods, remark, assignment, permitted device/proxy or local network, sync/session retention and fingerprint metrics. The options `configurationText` describes each field, values, defaults and conditions for all AI callers. Use actual choices only and explain `blockedReasons` instead of attempting a write with missing resources.
   Explicit generation such as “随便创建一个美团账号” permits `generateDefaults=true` for the named application's returned reference. The owner generates a DSphere account name, encrypted password and permitted defaults locally, then saves directly without form/confirmation/password prompts. Only explicit delegation such as “随便挑一个应用创建” permits `chooseAnyApplication=true` together with `generateDefaults=true`. Otherwise an omitted app opens an application picker. This creates a DSphere record, never registers a third-party account. Generated creation refuses an observed duplicate and preserves explicitly requested supported non-secret values. Current permissions/resources are rechecked before dispatch.
   Ordinary creation still requires the person's private password input, which you never answer; its Confirm/Decline sheet follows item 11. `VERIFICATION_CODE` does not request a password. No password, ciphertext, cookie, internal tag, header or credential reference is an MCP argument or result. `not-dispatched` / `input-required` means no business write was sent; use its missing fields and blocked reasons to correct the request only in this explicitly undispatched case. `update` merges permitted profile changes; `replaceCredential=true` requests trusted private input. Missing, declined or expired confirmation does not authorize continuation.
4. For an explicit deletion request, resolve a unique account from `list` and call `delete` directly. Built-in and external Agents delete without a confirmation dialog or a second chat confirmation. Do not read `get` just to print details. If the target is ambiguous, ask only which account. Current permissions, target occupancy and cancellation checks still apply. On `succeeded`, reply in one short sentence and stop, without further lookups. On `partial` with `data.saved=true`, report “account deleted; environment cleanup pending”; never delete again. `set-enabled` reads the target, toggles at most once when needed, and verifies it. The current APIs do not provide cross-client atomic set, create-only or global exactly-once semantics.
5. Before `open` (or `page.open` / `execution.run` with an `accountId`), resolve the account from the person's words only: the application they named and, when `list` returns several accounts for it, the account they named. When the application is unnamed (“打开我的账号”), unclear, or several accounts match, ask the person which one, naming the matching applications and accounts, and open nothing until they answer: with no task page yet, ask in your own conversation (the one exception to asking browser-task questions through `page.ask`); on a task page, `dsagent.page.ask` `kind: clarify` with the candidates as `options` and no `defaultOptionIndex`, so no countdown picks for them. Never pick the first row, the most recent or any other yourself; only explicit delegation such as “随便打开一个账号” / “open any account” lets you choose. `open` uses the existing account environment/fill owner. A page-opened result proves neither autofill nor login. `close` reuses synchronization and reports warnings while preserving uncertain contexts for recovery. `focus` locates existing account pages; it does not open a new environment.
6. `fingerprint.update` sets each fingerprint parameter on its own: put only the parameter to change in `patch`, and every other value stays. It covers the operating system and version, per-kernel browser version pools, a user agent redraw (`randomize_user_agent`), language, time zone, Do Not Track, port protection, WebRTC, geolocation, WebGL, WebGPU, screen mode and size, memory, CPU count and each on/off metric (`font_mode`, `battery_mode`, `canvas_mode` and the other `*_mode` fields: `privacy` or `noise` generates a value the way Work does, `real` uses the real one). Read the listed values from `fingerprint.options.get`. Related fields follow the Work form: changing the system redraws both user agents and the screen resolution. `fingerprint.regenerate` follows the current Work baseline. Already-open environments follow existing activation rules. **Never ask for or pass a cookie value:** `replaceCookie` asks the person in a SidePanel sheet and `clearCookie` removes it; reads report only `hasCookie`.
7. Network devices are the organization's IP proxies. `devices.options.get` gives the proxy types, IP versions, check channels, a suggested name and the capacity; `devices.list` and `devices.get` read them; `devices.create`, `update`, `delete`, `restore` and `test` manage third-party devices. Use only the returned `deviceId`. `devices.update` changes each setting on its own: put only the setting to change in `patch` (`name`, `proxyType`, `ipProtocol`, `host`, `port`, `checkChannel`, `remark`), and everything else stays. **Never ask the person to type a proxy username or password in the conversation and never pass one:** set `requestCredential` (create), or `replaceUsername` / `replacePassword` (update, each alone or together), and DSphere asks for just that value in its own SidePanel sheet, which shows where it will go. `clearUsername` and `clearPassword` remove one saved value. Changing the host, port, type or IP version is refused while a saved username or password would be kept, because it would go to the new address: replace or clear each saved value in the same call. `devices.test` runs the connection test Work's check button runs, through the device's saved settings, and returns `connectionTest` (`reachable`, `exitIp`, `country`, `countryCode`, `reportedToWork`). It updates the device's status in Work, and a failed test alerts the organization's operators, so test only when asked or after a change, and do not repeat it within 15 seconds. `UNAVAILABLE` means the browser's business extension is too old for it. Purchased platform devices are read-only here; buying, renewing and paying stay in Work.
8. `network.get` reads an account's connection. `network.set` moves up to 100 accounts to a device, the local network or none; DSphere always opens a Confirm sheet in its SidePanel, because the accounts' traffic moves (item 11). Accounts already open keep their connection until reopened.
9. `application.get`, `application.update` and `application.delete` manage custom applications. A rename is direct. An address change always opens a Confirm sheet, because saved accounts sign in on that address (item 11). An application with accounts or a platform template cannot be deleted.
10. Every write uses a fresh bounded idempotency key. Keep the returned operation reference; inspect `operations.get` under the same caller/session only when the result is pending or unknown. A timeout may have taken effect: use the gateway's operation reference for read-only lookup and check current state. Never repeat a deletion, toggle or open under another key to recover from an unknown result. `partial`, `waiting-user`, `failed`, `cancelled` and `outcome-unknown` do not mean full completion; a partial result may still confirm deletion as described above. Local operation records are not server receipts.
11. **Confirm sheets your own write opened.** A write that waits on the SidePanel's Confirm Account Operation sheet (fingerprint update or regenerate, update, replace or create, enable/disable, network connection, application address, device address or deletion, and an account open's sign-in on an unlisted site) answers `waiting-user` at once with an `agent-may-answer` warning when the person lets the asking agent answer it (Settings → Account Confirmations, person-only, default on). Then call `accounts.confirmations.list` and `accounts.confirmations.answer` with the listed `interactionId` and `confirm` or `decline`. Confirm only the change the person asked for in their own words, decline one they did not ask for, and when unsure ask the person instead of answering. Afterwards read the write's result with `operations.get` under its `operationId` (an open: its `autofill` receipt); the answer alone proves nothing, and never resubmit the write. The person may answer first: the first answer stands, and a later one is refused (`TARGET_NOT_FOUND`). `POLICY_DENIED` with `AGENT_ANSWER_OFF` means the person keeps answers to themselves: tell them once that the sheet waits in the SidePanel and poll. Only your own sheets are listed; password, cookie, proxy-credential and configuration sheets always stay the person's, as does every other caller's sheet. Without the warning (`person-notified`), the person answers.

Required human interactions appear in the conversation for non-secret configuration, with separate trusted consent/credential input where required. Explicit deletion executes directly without these interactions. Frontend and Sidepanel share the same Extension account owner through the in-process tool surface; external AI reaches that owner through the existing Native MCP gateway. Native contains no account business implementation.
